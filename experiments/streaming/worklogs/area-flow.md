## Recommendation

### Flow: plain Yosys + OpenSTA-free area report, not Hammer
Hammer/OpenROAD buys placement and timing we do not need. We need synthesized cell area only. Use a small
Yosys script run directly on the existing generated Verilog. Lightest option; no Chipyard elaboration for the
three existing configs. (Hammer's yosys wrapper would need the full ChipTop `make syn` path and PDK downloads.)

### PDK and cell library
| Option | Pros | Cons | License (verify before citing) |
|---|---|---|---|
| Nangate45 (FreePDK45 based) **recommended primary** | one Liberty file, small, standard in academic papers, supported by Yosys/OpenROAD flows | not a real foundry process; absolute um^2 are 45 nm predictive | NanGate Open Cell Library, open for research [verify exact terms] |
| ASAP7 (7 nm predictive) | modern node, BSD-3 | Liberty is split per corner and gzipped; some cells and flops need care in abc mapping; tiny um^2 | BSD-3 (ASAP7 PDK) [verify] |
| sky130 HD (cross-check) | real open foundry PDK, Apache-2.0 | large cells, 130 nm | Apache-2.0 |
Recommended: Nangate45 for the headline Pareto; one sky130hd run of stock + nm24 as a sanity check that the
percent overhead is not library-specific. Report ratios (% over stock) as the main claim; absolute um^2 are
technology-specific and labelled so. Exact Liberty/PDK source and its license text must be copied into the
results folder when downloaded (user approval needed, see below).

### SRAM handling
Primary: blackbox the three Gemmini SRAM types (`mem_ext`, `mem_0_ext`, and `mem_1_ext` if inside Gemmini) and
report them separately as bits (derived from `.mems.conf`: 4 x 4096 x 128 + 2 x 512 x 512 bits = 2,097,152 + 524,288
= 2,621,440 bits, 320 KiB, before checking `mem_1_ext`). Because the SRAM bits are identical across configs, the SRAM
term cancels in the delta and the headline is logic-area % over stock.
Optional: an SRAM area number via a FakeRAM-style model. Options: the OpenRAM/FakeRAM2.0 generators or bsg
`bsg_fakeram`, or Hammer `sram_compiler` (nangate45/asap7 entries in `sram-cache.json`). These give macro areas
for the listed depth x width. Label them as a model, not a measurement. Do not synthesize the `_ext` reg arrays:
a 2.6 Mbit behavioural array would become flops, grow area by orders of magnitude and take hours. The Pareto should
plot logic area (primary) with the SRAM model area as a constant offset (optional second axis).

### How to report
- Per config: total logic cell area (um^2), flop count, cell count, SRAM bits (separate), SRAM model area (optional,
  labelled).
- % over stock = (cfg logic - stock logic) / stock logic, same tool run, same script and library (rule 4 analogue:
  compare only within the same flow and Liberty).
- Per-submodule table (from `stat -top Gemmini` hierarchy) for the sparse additions: `ExecuteController`
  (`nm_meta_q`), `Mesh`/`PE_*` (mux/select logic), `LoopMatmul*`, new `Queue4_Vec16_*` and `ram_*`, with stock
  vs cfg side by side. Every number cites the `stat` log line.

## Risks
1. Plain Yosys may fail to parse firtool SV (packed structs/arrays, `assume`/`assert`, `initial` blocks). Mitigation:
   `-DSYNTHESIS`, `sv2v`, or `yosys-slang`. Adds 0.5 to 1 day [E].
2. Floating-point units / hardfloat modules in the file list may only belong to Rocket's FPU; confirm Gemmini top
   closure via `hierarchy -top Gemmini` (unused files drop out).
3. abc area depends on target clock and effort; an area number is a mapping result, not signoff. State this in the paper.
4. Blackbox SRAM stubs must match ports exactly; misuse would silently remove memory-side logic (read-mux, masks).
5. Absolute um^2 are predictive-PDK numbers; ratios are the defensible output.
6. Future configs change `gemmini_params.h` during elaboration; keep scratch dirs, do not touch Berkeley sources.
